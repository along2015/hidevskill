# 阶段规约与质量检查清单

按需读取对应章节。每个阶段包含：目标、必须完成项（产出规约）、质量清单、用户确认标准。

---

## 限制条款规约（全阶段适用）

**目标**：通过限制配置文件保护项目中不允许改动的代码与资源，防止误改、误删。

**配置文件**：
- 项目级：`docs/specs/RESTRICTIONS.md`（项目尚无该文件时，`new_spec.py` 会从 `assets/templates/RESTRICTIONS.md` 自动创建）。
- 需求级：`docs/specs/req-{NNN}-{slug}/restrictions.md`（可选，与项目级叠加生效，需求级可加严不可放宽）。

**条款类型**：

| 条款 | 含义 |
|---|---|
| 禁改清单 | 文件/目录通配符列表，禁止任何形式修改（含重命名、复制后改、间接脚本改） |
| 禁删清单 | 禁止删除的文件/目录 |
| 需评审清单 | 修改前必须先向用户展示变更方案并获明确同意 |
| 禁执行清单 | 禁止执行的命令/操作（如数据删库、git 历史改写、生产环境操作） |

**执行规则**：
1. 跨对话协议检查时随 INDEX.md 一并读取，作为全程上下文。
2. 阶段 3 产出"涉及文件清单"后逐项比对，冲突项立即向用户提出并记录到 README.md 待澄清清单。
3. 阶段 5 每个任务动手前核对本任务改动文件清单；命中禁改条款时**停止并报告**，不得静默绕过。
4. 用户明确批准修改受限项时方可执行，并在 README.md"豁免记录"登记（对象、理由、日期）。
5. 阶段 6 测试时结合 `git status` / diff 抽查，验证受限项未被改动，结果写入 06-acceptance.md。
6. 配置文件本身不存在且用户未要求创建时，提示用户；绝不在无限制配置时默认"没有限制"而跳过提示。

## 阶段 1：需求澄清（01-requirements.md）

**目标**：把模糊描述转化为边界清晰、可验收的需求说明。

**必须完成项**：
- 背景与问题：为什么做，现状痛点。
- 目标与成功度量：可量化的目标（有则填，无则说明）。
- 用户故事：`作为<角色>，我希望<动作>，以便<价值>`，每条带 US-ID。
- 功能需求：FR-编号，逐条可测试。
- 非功能需求：性能、兼容性、安全、可用性等，明确适用范围。
- 边界与约束：不做什么（out of scope）、技术/业务约束；**涉及受限代码的约束项在此显式登记**。
- 疑问与澄清记录：向用户提出的问题、答案、仍未决项。
- 验收标准草案：AC-编号，与用户故事/功能需求对应，是阶段 6 的唯一依据。

**质量清单**：
- [ ] 每条功能需求可测试、无歧义（避免"尽量""等""合理"类词）。
- [ ] 明确写出"不做什么"。
- [ ] 未决问题已列入 README.md 待澄清清单。
- [ ] 用户已对需求范围表示确认。

## 阶段 2：概要设计（02-high-level-design.md）

**目标**：确定整体技术方案与模块边界，先于细节。

**必须完成项**：
- 方案概述：一段话说清整体思路；如有多方案，列出对比与选型结论。
- 架构/模块划分：模块图（mermaid 优先）、各模块职责、依赖方向。
- 技术选型：框架/库/组件的选择及理由，贴合项目现有技术栈。
- 数据概要：涉及的核心数据实体与关系（详细字段留到阶段 3）。
- 接口概要：系统间/前后端的核心接口清单（签名级即可）。
- 关键流程：核心场景的流程图或时序图。
- 风险与权衡：主要风险点与应对（含触碰受限代码的风险）。

**质量清单**：
- [ ] 模块职责无重叠、依赖方向清晰。
- [ ] 技术选型与项目现有技术栈一致或给出引入理由。
- [ ] 关键流程覆盖需求中的每个用户故事。
- [ ] 用户已对方案方向表示确认。

---

## 阶段 3：详细设计（03-detailed-design.md）

**目标**：细化到可直接照此编码的程度。

**必须完成项**：
- 数据设计：表结构/存储结构完整字段定义（字段、类型、约束、索引、默认值）。
- 接口设计：每个接口的路径、方法、参数、响应结构、错误码、示例。
- 组件/函数设计：新增或修改的组件、函数签名、职责、关键算法伪代码。
- 状态机与异常处理：分支状态、失败路径、降级与重试策略。
- 涉及文件清单：预计新增/修改的文件路径列表（阶段 5 按此核对）。**产出后逐项与 RESTRICTIONS.md 禁改/需评审清单比对**。
- 兼容与迁移：存量数据/接口的兼容策略，需要的迁移脚本。

**质量清单**：
- [ ] 每条功能需求都能在设计中找到落点（可反向核对）。
- [ ] 接口契约完整（含错误路径），无"后续补充"。
- [ ] 涉及文件清单与项目实际结构核对过。
- [ ] 涉及文件清单与限制条款比对完成，冲突项已向用户提出。
- [ ] 用户已确认设计细节。

---

## 阶段 4：任务拆解（04-tasks.md）

**目标**：把设计切成可独立执行、可独立验证的任务。

**必须完成项**：
- 任务清单：每条含 T-ID、标题、描述、关联需求（FR/US 映射）、关联设计章节、预估工作量、状态（pending|in-progress|done|blocked）。
- 依赖关系：任务间前后依赖，标注关键路径。
- 里程碑（可选）：任务较多时按可演示节点分组。

**质量清单**：
- [ ] 单个任务可在一次会话内完成，避免大颗粒任务。
- [ ] 每个任务有明确的完成判据（可验证的产出）。
- [ ] 所有功能需求至少被一个任务覆盖，无遗漏。
- [ ] 用户已确认拆解粒度与顺序。

---

## 阶段 5：编码实施（05-implementation.md）

**目标**：按任务执行编码并留痕，保证过程可追溯、可续作。

**必须完成项**（逐任务追加）：
- 任务 ID 与标题。
- 改动文件列表（新增/修改/删除）。
- 限制条款核对结果：本任务改动文件与禁改清单的比对结论（无冲突 / 已获豁免并登记）。
- 关键实现说明：重要逻辑、坑点、与设计的对应关系。
- 设计偏离记录：凡与 03-detailed-design.md 不一致处，登记偏离点、原因、影响面。
- 验证结果：构建/lint/本地运行结果。

**执行规则**：
- 严格按 04-tasks.md 顺序与依赖推进；每完成一个任务同步更新其状态。
- 每个任务动手前核对 RESTRICTIONS.md；命中禁改条款时停止并报告，获用户豁免后执行并登记。
- 项目有构建/测试命令时，每任务后执行并循环修复至通过；无法修复时如实报告完整错误上下文。
- 不得通过删除代码、关闭校验、注释报错语句来消除错误。
- 会话中断前，将当前任务状态与未完事项写入 README.md。

## 阶段 6：功能测试验收（06-acceptance.md）

**目标**：以验收标准为纲完成功能验证并闭环，留存截图证据，并产出独立测试报告。

### 6.1 测试执行规约

**必须完成项**：
- 测试环境说明：执行环境（本地/测试服）、构建版本、数据库/依赖版本、测试账号。
- 测试用例表：每条含 TC-ID、关联验收标准（AC 映射）、前置条件、步骤、预期、实际、结果。
- 截图证据：见 6.2。
- 限制项核查：按限制条款规约第 5 条，验证 RESTRICTIONS.md 所列受限项未被改动，记录核查方式（如 git diff 抽查）与结论。
- 缺陷记录：BUG-ID、现象、根因、修复方式、回归结果。
- 测试范围说明：覆盖了什么、未覆盖什么及原因（如依赖环境）。
- 验收结论：全部通过 / 带遗留项通过 / 不通过，及用户最终确认记录。
- 遗留项清单：转入后续迭代的事项。

### 6.2 测试截图规约

- 存放目录：`docs/specs/req-{NNN}-{slug}/screenshots/`（`new_spec.py` 自动创建）。
- 命名：`{TC-ID}-{步骤或场景}.png`，如 `TC-3-submit-form-success.png`；同一用例多步截图按 `TC-3-step1.png` 递增。
- 截图时机：
  - 涉及页面/界面/可视化效果的验证项：使用浏览器工具**实际打开页面执行操作并截图**，不得凭想象描述界面。
  - 关键状态节点：成功态、失败态、边界态各留一张。
  - 缺陷现场：记录 BUG 前先截图存证，修复回归后再截一张对比。
- 引用方式：在 06-acceptance.md 与 07-test-report.md 中以相对路径引用：`![TC-3 提交成功](screenshots/TC-3-submit-form-success.png)`。
- 无法截图时（纯后端接口/无界面），在对应用例行注明"无界面，以接口响应/日志为证"，可粘贴关键响应或日志摘录（注意脱敏）。
- 截图质量：确保关键信息（标题、状态、数据）清晰可辨；含敏感信息（密码、token、手机号）时打码或脱敏后再保存。

### 6.3 测试报告规约（07-test-report.md）

- 时机：验收阶段全部用例执行完毕、缺陷闭环后生成；验收中途可生成"阶段性测试报告"（标注状态为进行中）。
- 独立性：07-test-report.md 是**可直接交付/归档的独立文档**，不依赖读者了解 specs 目录其他文档；关键上下文（需求标题、验收标准）需在报告内自含。
- 必含章节：报告摘要（结论、通过率、缺陷数）、测试环境、测试范围、用例执行汇总表、截图证据、缺陷清单、限制项核查结论、遗留项与建议。
- 与 06-acceptance.md 的关系：06 是过程记录，07 是对外报告；两者结论必须一致，不一致时以用户确认的最新结论为准并回写 06。
- 生成后向用户展示报告摘要并交付。

**质量清单**：
- [ ] 每条验收标准至少对应一个用例。
- [ ] 界面类用例均有截图证据且在文档中正确引用；无界面用例注明替代证据。
- [ ] 每个缺陷有回归验证记录。
- [ ] 受限代码核查完成并记录结论。
- [ ] 07-test-report.md 已生成且与 06-acceptance.md 结论一致。
- [ ] 用户已最终确认验收结论。
- [ ] README.md 状态更新为 accepted。

## 附录：跨对话续作检查清单

恢复中断的需求时按序执行：

1. 读 `docs/specs/<requirement-id>/README.md` 状态看板，确定当前活动阶段。
2. 读当前阶段文档全文 + README.md 待澄清清单。
3. 读 `docs/specs/RESTRICTIONS.md`（及需求级 restrictions.md），刷新限制条款上下文。
4. 若在阶段 5，另读 04-tasks.md 找到第一个未完成任务，并浏览 05-implementation.md 最近几条变更记录。
5. 若在阶段 6，另查看 screenshots/ 目录已有截图与 07-test-report.md 当前状态（未生成/进行中/已完成）。
6. 向用户简报："当前处于阶段 X，已确认的关键决策是…，下一步是…，待澄清问题有…，受限项核查结论是…"，获得用户认可后再动手。
