# Hi Dev Plus Skill（增强版）

## Overview

将一个软件需求从模糊描述推进到验收完成，全程以文档为唯一事实来源（Single Source of Truth）。六个阶段依次为：

1. **需求澄清**（requirements）
2. **概要设计**（high-level-design）
3. **详细设计**（detailed-design）
4. **任务拆解**（tasks）
5. **编码实施**（implementation）
6. **功能测试验收**（acceptance）

每个阶段产出一份按规约组织的 markdown 文档，集中存放在项目内 `docs/specs/req-{序号}-{slug}/` 目录；`README.md` 作为该需求的状态看板记录各阶段状态与关键决策，是实现**跨对话上下文延续**的核心机制。项目内**多个需求**通过项目级汇总索引 `docs/specs/INDEX.md` 统一登记与查看。

相对初版的**三项增强能力**：

| 能力 | 说明 |
|---|---|
| 限制条款机制 | 读取项目 `docs/specs/RESTRICTIONS.md` 限制配置文件，全程保护禁改代码/资源，任何阶段不得违反 |
| 测试截图存证 | 阶段 6 执行测试时，对页面/界面类验证留存截图至 `screenshots/` 目录并在文档中引用 |
| 独立测试报告 | 验收完成后自动生成 `07-test-report.md`，可直接交付或归档 |

## 限制条款机制（首要安全规则）

### 限制配置文件 docs/specs/RESTRICTIONS.md

- 位置：项目根目录 `docs/specs/RESTRICTIONS.md`（项目级全局限制）；需求目录内可另放 `restrictions.md`（需求级补充限制，与全局叠加生效）。
- 模板：`assets/templates/RESTRICTIONS.md`；`scripts/new_spec.py` 在项目尚无该文件时自动从模板创建。
- 内容结构：禁改清单（文件/目录通配符）、禁删清单、需评审后才能改清单、禁执行操作清单、生效范围与豁免审批人。

### 执行规则（优先级从高到低）

1. **用户实时明确指令**：用户在当前对话中明确要求修改某个受限项时，按用户指令执行，但必须在 README.md 的"豁免记录"中登记（对象、理由、日期）。
2. **RESTRICTIONS.md 限制条款**：任何阶段（尤其阶段 5 编码）动手前，先核对禁改清单；命中即**停止操作并向用户报告**，绝不静默绕过（包括通过重命名、复制后修改、间接脚本等方式变相触碰）。
3. 通用安全底线：不得删除代码或关闭校验来"消除"错误；不得改动 git 历史；不得执行破坏性命令。

### 检查时机

- 跨对话协议检查时：与 INDEX.md 一并读取 RESTRICTIONS.md，将其作为全程上下文。
- 阶段 3（详细设计）"涉及文件清单"产出后：逐项与禁改清单比对，冲突项立即向用户提出。
- 阶段 5（编码实施）每个任务动手前：核对本任务改动文件清单。
- 阶段 6（测试验收）：验证受限项未被改动（可结合 `git status`/diff 抽查）。

## 跨对话上下文协议（首要规则）

每次对话开始处理任何开发相关请求时，执行以下检查：

1. 检查项目根目录下是否存在 `docs/specs/` 目录。
2. **若存在**：先读取 `docs/specs/INDEX.md` 汇总索引掌握全部需求及状态；若索引缺失（旧结构项目），列出各需求目录并读取各自 `README.md` 重建索引后再继续。若用户请求与某个已有需求相关（如"继续""恢复""下一步"），先完整阅读该需求的 `README.md` 和当前活动阶段文档，再从中断点继续，**不要重新开始或重复提问已澄清的内容**。
3. **同时**读取 `docs/specs/RESTRICTIONS.md` 限制配置文件（不存在时提示用户是否创建），后续所有阶段遵守其中的限制条款。
4. **若不存在**：按下方"新需求流程"创建目录结构。

## 新需求流程

### 1. 建立文档结构

执行 `scripts/new_spec.py` 创建文档骨架（自动取号并登记汇总索引）：

```bash
python <skill目录>/scripts/new_spec.py <slug> --title <需求标题> [--path <项目根目录>] [--priority P0|P1|P2]
```

- `slug`：需求语义短横线小写标识（如 `middleware-info-module`）。若用户未提供，从需求描述提炼一个。
- 脚本自动：分配 `REQ-{NNN}` 编号 → 在 `<项目根目录>/docs/specs/req-{NNN}-{slug}/` 下从 `assets/templates/` 生成 8 个文档（含 `07-test-report.md`）并创建 `screenshots/` 目录 → 项目尚无 `docs/specs/RESTRICTIONS.md` 时从模板创建限制配置 → 在 `docs/specs/INDEX.md` 需求清单登记并更新状态统计。
- 无脚本可用时，手工按编号规则建目录、按 `assets/templates/` 模板逐一创建文件，并在 INDEX.md 登记新行。

### 2. 阶段推进规则

- 严格按阶段顺序推进，**不得跳过**。前序阶段文档未获用户确认时，不得开始下一阶段。
- 每个阶段开始前，阅读 `references/phase-guide.md` 中对应阶段的规约（产出要求、质量检查清单、确认标准）。
- 每个阶段结束时：
  - 将该阶段文档填写完整；
  - 向用户展示文档核心内容并请求确认；
  - 用户确认后，更新 `README.md` 看板：将该阶段状态改为 `done`，下一阶段改为 `in-progress`，并追加"关键决策/结论"摘要行。
- 若某阶段由用户明确豁免（如极简改动跳过详细设计），在 README.md 的"豁免记录"中注明理由，不得静默跳过。

### 3. 阶段文档与规约对照

| 阶段 | 文档 | 核心产出 |
|---|---|---|
| 需求澄清 | `01-requirements.md` | 背景/目标、用户故事、功能与非功能需求、边界与疑问清单、验收标准草案 |
| 概要设计 | `02-high-level-design.md` | 架构方案、模块划分、技术选型、数据/接口概要、关键流程图 |
| 详细设计 | `03-detailed-design.md` | 表结构/接口契约、组件与函数级设计、状态与异常处理、涉及文件清单 |
| 任务拆解 | `04-tasks.md` | 带 ID 的任务清单、依赖关系、工作量估计、任务-需求映射矩阵 |
| 编码实施 | `05-implementation.md` | 按任务记录的变更日志、关键实现说明、偏离设计的决策记录 |
| 功能测试验收 | `06-acceptance.md` | 测试用例与执行结果、截图证据、缺陷记录与闭环、验收结论与遗留项 |
| 测试报告 | `07-test-report.md` | 独立可交付的测试报告（摘要、环境、用例汇总、截图证据、缺陷与结论） |

详细阶段规约与质量清单见 `references/phase-guide.md`（按需加载对应阶段章节即可，不必一次全文读取）。

### 4. 编码实施阶段的特别要求

- 编码严格以 `03-detailed-design.md` 与 `04-tasks.md` 为依据；实现若需偏离设计，先在 `05-implementation.md` 的"设计偏离记录"中登记偏离点与理由，再动手修改。
- **每个任务动手前先核对 RESTRICTIONS.md 禁改清单**（见"限制条款机制"）。
- 每完成一个任务：更新 `04-tasks.md` 中该任务状态，并在 `05-implementation.md` 追加变更记录（任务 ID、改动文件、要点）。
- 若项目存在自动构建/测试命令，任务完成后立即执行并消除错误，循环至通过；失败且无法自动修复时如实报告，不得通过删除代码或关闭校验来"消除"错误。

### 5. 功能测试验收阶段的特别要求（增强）

- 以 `01-requirements.md` 中的验收标准为唯一依据设计测试用例，逐条回填执行结果。
- **测试截图**：涉及页面/界面/流程可视效果的验证项，使用浏览器工具实际执行并截图，保存到 `docs/specs/req-{NNN}-{slug}/screenshots/`（命名如 `TC-1-step2.png`），在 06-acceptance.md 对应用例行引用；无法截图时（纯后端/无界面）注明原因即可。
- 存在未通过项时记录缺陷、修复并回归；全部通过后由用户最终确认，README.md 中整单标记 `accepted`。
- **测试报告**：验收完成后，将 06-acceptance.md 的内容整理为独立的 `07-test-report.md` 测试报告（含摘要、环境、用例汇总表、截图证据、缺陷清单、验收结论），向用户交付；报告规约见 `references/phase-guide.md` 阶段 6 章节。

## 状态看板 README.md 规约

`README.md` 是单个需求跨对话续作的关键，必须始终保持最新。核心字段：

- **需求编号**：REQ 编号与需求 ID，与 INDEX.md 保持一致。
- **状态总览表**：每行一个阶段，含 `阶段 / 文档 / 状态（pending|in-progress|done|exempt）/ 确认人 / 关键决策摘要`。
- **当前活动阶段**：一眼可见的唯一 `in-progress` 项。
- **待澄清问题清单**：未关闭问题的持续累积，跨阶段、跨对话均有效。
- **豁免记录**：受限项经用户批准修改的登记处（含绕过限制的临时授权）。
- **变更历史**：每次阶段推进或重大决策追加一行（日期 + 摘要）。

对话结束时若处于某阶段中途，必须将当前进展、未决问题写入 README.md，保证下次对话可无损接续；同时同步更新 `docs/specs/INDEX.md` 中该需求的状态行。

## 用户常用指令映射

| 用户说 | 动作 |
|---|---|
| "做个新功能 / 实现 XX 需求" | 跨对话协议检查 → new_spec 自动取号建档并登记 INDEX → 进入阶段 1 |
| "继续上次的需求 / 接着做" | 读 INDEX.md / README.md / RESTRICTIONS.md → 报告进度 → 从当前阶段继续 |
| "需求清单 / 需求汇总 / 进度如何" | 读取 docs/specs/INDEX.md（缺失时扫各 README.md），汇报全部需求的编号、状态与进度 |
| "归档 XX 需求 / 直接归档" | 按规约补录 8 份阶段文档，README 标记 accepted，INDEX 状态改为 accepted |
| "跳过设计直接写代码" | 在 README.md 登记豁免理由后执行 |
| "这个需求验收完成了吗" | 读取 06-acceptance.md 与 README.md 汇报结论 |
| "出一份测试报告 / 生成测试报告" | 依据 06-acceptance.md 整理生成 07-test-report.md 并交付 |
| "哪些代码不能动 / 限制有哪些" | 读取并汇报 docs/specs/RESTRICTIONS.md（及需求级 restrictions.md）内容 |
